---- Purpose/Functionality --------------------------------------------------------------------------

Plays a local video file by embedding libvlc ( via the python-vlc ctypes
bindings ) into a plain QFrame, using the frame's native window handle (
winId() -> vlc_player.set_xwindow() on Linux/X11 ). Demonstrates the
"bulletproof" option for playing video in Qt: libvlc/VLC decodes almost
any codec/container a user throws at it, at the cost of a new runtime
dependency ( libvlc / the VLC package itself must be installed ) and a
slightly fiddlier embed pattern than QMediaPlayer or QWebEngineView.


---- Development History --------------------------------------------------------------------------

    * Started from a template stub ( imports for QWebEngineView left over
      from copy/paste, buttons wired to methods that just printed a
      message ). vid_1/vid_2 file names were already set: a vp9/opus webm
      test clip, and an original-codec H.264/AAC phone mp4.

    * Checked the target machine before writing any code: X11 session (
      $XDG_SESSION_TYPE = x11, no $WAYLAND_DISPLAY ) confirmed set_xwindow()
      would work directly -- this would have been a real gotcha under a
      pure Wayland session, which has no equivalent of set_nsobject() for
      Linux. Also confirmed libvlc.so.5 already present system-wide (
      apt-installed VLC ), so only the python-vlc ctypes bindings needed
      adding, not libvlc itself.

    * Rewrote the module:
        - dropped the QWebEngineView imports, added "import vlc"
        - QFrame as the video surface ( black QPalette so nothing shows
          before playback starts -- libvlc paints directly into the
          frame's native window, bypassing Qt's own paint system entirely,
          so Qt's normal widget-fill color would otherwise flash/show
          through )
        - vlc.Instance() / vlc_instance.media_player_new() created once in
          _build_gui_widgets
        - embedding ( winId() -> set_xwindow() ) done lazily on first Play
          click ( _ensure_embedded() ), not at gui-build time -- winId()
          should be called after the frame is part of a shown widget
          hierarchy, and this tab's __init__ runs before the main window
          has shown anything
        - libvlc fires its player-state events ( Playing/Paused/Stopped/
          EndReached/EncounteredError ) on a libvlc-internal thread, not
          the Qt main thread -- unlike QMediaPlayer, which already
          marshals its signals onto the Qt thread for you. Added a
          class-level Signal( str ) ( vlc_state_signal ), emitted from the
          ( otherwise do-nothing ) libvlc event callbacks and connected to
          on_media_state_changed(), which is the only place that actually
          touches self.media_status_widget. Qt's queued-connection
          semantics do the thread hop safely.
        - Pause button calls vlc_player.pause(), which libvlc treats as a
          toggle ( pause if playing, resume if paused ) -- simplest
          option for a 4-button demo, see Limitations.
        - Stop button calls vlc_player.stop().

    * uv/environment side-quest ( not part of the tab's design, but part of
      this session's process ):
        - "uv add python-vlc" ( no --active ) created a stray project-
          local .venv instead of touching the already-active Spyder
          interpreter ( spy_py_13_qt_5 ) -- removed that stray .venv.
        - "uv add --active python-vlc" was then used, which -- unexpectedly
          -- deleted and fully rebuilt spy_py_13_qt_5 from scratch,
          keeping only the packages pyproject.toml already declared. This
          silently dropped pip itself, spyder-kernels, and PyQtWebEngine (
          none of which had been declared in pyproject.toml even though
          the app needs PyQtWebEngine just to import main.py, and Spyder
          needs spyder-kernels to reconnect ). Recovered by reinstalling
          spyder-kernels + pip immediately, and PyQtWebEngine once it
          surfaced as a hard import-time blocker while test-running the
          app. pyproject.toml now declares all four so this doesn't
          silently regress again.

    * Verification: rather than trust a visual inspection alone, wrote a
      throwaway harness ( drive_vlc_tab.py, not part of the app ) that
      boots the real app via pyqt_by_example.PyqtByExample(), opens this
      tab the same way the app's own "Select Tab" search does (
      window.open_tab_select( "tab_vlc_qt_widget", "QWebVlcMediaWidgetTab",
      ... ) ), and drives Play Vid 1 / Pause / Stop / Play Vid 2 via
      QTest.mouseClick() on the real buttons.
        - First attempt screenshotted via QWidget.grab() -- came back
          solid black even though the status label correctly said
          "playing" and get_state() confirmed real playback. Root cause:
          grab()/render() only capture Qt's own paint buffer; libvlc
          draws directly into the frame's raw X11 window, entirely
          outside Qt's rendering pipeline, so Qt-side screenshots
          structurally cannot see it.
        - Confirmed the Playing -> EndReached -> Stopped event sequence
          directly against libvlc ( a standalone event-manager script )
          to explain why the short phone-clip test showed "stopped" only
          ~1-2s after being clicked -- it had actually played to
          completion already, that is correct behavior, not a bug.
        - To get a real visual check, temporarily added mss ( "uv add
          --active mss", removed again afterward with "uv remove --active
          mss" -- test-only, not a project dependency ) and captured a
          genuine X11 screen region grab of the video_frame's on-screen
          rect mid-playback. This showed the actual movie frame ( the
          film's opening China Film Bureau certification card ) rendering
          inside the embedded QFrame, confirming the embed genuinely
          works end to end.

    * Added position ( seek ) and volume controls, matching vlc's own
      player chrome:
        - a QSlider ( 0-1000, scaled against vlc_player.get_length()/
          set_time(), both in ms ) plus a "mm:ss / mm:ss" QLabel, kept in
          sync by a QTimer polling every 250ms
        - polling rather than subscribing to libvlc's own
          MediaPlayerPositionChanged/TimeChanged events deliberately --
          those fire often and on the libvlc thread, more thread-marshal
          traffic than a seek bar needs; a Qt-side timer calling
          get_time()/get_length() is simpler and plenty smooth at 250ms
        - self.position_slider_dragging guards against the timer fighting
          the user's drag: sliderPressed sets it True ( stop overwriting
          the slider mid-drag ), sliderReleased seeks via set_time() and
          clears it
        - a second QSlider ( 0-100 ) wired straight to
          vlc_player.audio_set_volume(), default 80
        - verified against the real running app the same way as the
          buttons: pressed/dragged/released the position slider
          programmatically, confirmed vlc_player.get_time() landed at the
          expected offset ( to within libvlc's normal keyframe-seek
          tolerance ) and a fresh mss capture showed a genuinely different
          scene in the video after the seek; drove the volume slider and
          confirmed vlc_player.audio_get_volume() tracked it exactly

---- Capabilities ( what works ) --------------------------------------------------------------------------

    * Plays local video files in effectively any codec/container libvlc
      supports -- tested with both a vp9/opus webm and an original H.264/
      AAC phone-camera mp4, both played correctly ( unlike the
      QWebEngineView experiment, which cannot play the H.264/AAC file at
      all -- see Discussion ).

    * Play Vid 1 / Play Vid 2 / Pause / Stop all wired to the real
      vlc.MediaPlayer.

    * Status label reflects the real player state ( playing / paused /
      stopped / end reached / error: ... ), updated safely from libvlc's
      background thread via a Qt signal.

    * Position slider shows/sets playback position ( drag to seek,
      confirmed accurate to within libvlc's normal keyframe-seek
      tolerance ), with a live "mm:ss / mm:ss" elapsed/total label.
      Volume slider controls playback volume directly.

    * Standard tab scaffolding ( mutate_0/1, inspect, breakpoint, copy-
      module-file-name, github-wiki, help-file ) present via
      tab_base.TabBase, same as sibling tabs.

    * Verified against the real running app, not just a standalone
      script -- see Development History.


---- Limitations ( what does not, and why ) --------------------------------------------------------------------------

    * !! X11 only. set_xwindow() is the Linux/X11 embed call; a pure
      Wayland session has no direct equivalent ( set_nsobject() is macOS-
      only, set_hwnd() is Windows-only ) and would need XWayland or a
      different libvlc video-output setup. This machine is X11, so the
      Wayland case is unverified.

    * No explicit vlc_instance/vlc_player.release() on tab or app
      teardown. QMediaPlayer is owned/cleaned-up by Qt; libvlc's objects
      are not. Accepted as a minor risk here since tabs in this app
      persist for the whole app lifetime and there's no reliable per-tab
      close hook in this app's architecture anyway ( child tab widgets
      don't get their own closeEvent when the app quits ).

    * Pause is a toggle ( libvlc's vlc_player.pause() behavior ), not a
      dedicated pause-only action -- clicking it while already paused
      resumes playback instead of doing nothing.

    * Error messages ( from vlc.libvlc_errmsg() ) are often empty/None --
      libvlc is inconsistent on Linux about setting this, so the error
      path can surface "unknown libvlc error" instead of a real reason.

    * Not wired into the app's tab-selection registry automatically --
      same situation as the QWebEngineView experiment tab; opened here
      only through dir_for_tabs auto-discovery / the "Select Tab" search,
      not any default-open list.

    * STATUS / HOW_COMPLETE in the module docstring are rough, not
      re-benchmarked against the app's own scale.


---- Interaction --------------------------------------------------------------------------

    * <Play Vid 1>  loads/plays self.vid_1_file_name ( vp9/opus webm test
        clip )

    * <Play Vid 2>  loads/plays self.vid_2_file_name ( original-codec
        H.264/AAC phone mp4 -- plays fine here, unlike the QWebEngineView
        tab's equivalent button )

    * <Pause>  toggles pause/resume on the vlc player

    * <Stop>  stops the vlc player

    * <position slider>  drag to seek anywhere in the current media;
        updates automatically while playing ( disabled while you're
        actively dragging it )

    * <volume slider>  sets playback volume directly, 0-100

    * <mutate-examine> / <wat-inspect> / <breakpoint-debug>  the usual
        tab_base scaffolding, mostly stubs ( mutate_0/mutate_1 ) for now

Widgets included:
    QFrame ( video surface ), QLabel ( status, time ), QPushButton x4,
    QSlider x2 ( position, volume ), QTimer ( polls position )


---- Discussion -- python-vlc vs QMediaPlayer vs QWebEngineView --------------------------------------------------------------------------

    This project now has three separate "play a video" experiments, each
    with a real, demonstrated tradeoff:

    python-vlc + QFrame ( this tab ) pros: eats almost any codec/container
    without transcoding, the most "bulletproof" of the three. cons: new
    runtime dependency ( libvlc / VLC itself must be installed on the
    target machine, not just a pip package ); embedding is X11-specific (
    winId()/set_xwindow(), see Limitations ); libvlc's events arrive on a
    foreign thread, requiring the Qt-signal marshaling this tab adds.

    QMediaPlayer/QVideoWidget ( tab_media_widget.py ) pros: pure Qt, no
    extra runtime install, Qt marshals its own signals for you already.
    cons: on this machine goes through GStreamer, so behavior depends on
    whatever GStreamer plugins happen to be installed on the target
    machine -- less self-contained than "install VLC" or "use the
    QtWebEngine that's already bundled".

    QWebEngineView ( tab_webengine_widget.py ) pros: no new Qt module
    needed ( already used elsewhere in this project ), free scrubber UI
    from the browser's native <video controls>. cons: PyQt5's bundled
    Chromium has no H.264/AAC decode at all ( licensing ), so it can only
    play already-open-codec files -- confirmed unable to play the same
    H.264/AAC phone mp4 that this tab plays without any conversion.


---- Questions --------------------------------------------------------------------------

    * Is the goal three separate demo tabs ( one per backend, as now ), or
      should this eventually collapse into one "play video" tab with a
      selectable backend? The three now cover meaningfully different
      tradeoffs, so keeping them separate seems more useful as reference
      material.

    * Worth adding an explicit release() on the vlc Instance/MediaPlayer
      somewhere reachable ( e.g. a manual "release" button, or on_close if
      one is ever added to TabBase ), given this app's tabs otherwise
      never get torn down individually?
